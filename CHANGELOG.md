## [4.2.0] - 2026-09-27

### Added

- Parity: the spec 4.1.0 pipeline conformance corpus is adopted and closed to green. The corpus (219 cases, spec 4.1.0, byte-identical to the guard-core specs fixtures) now drives both gates: the detect runner (184 cases) and the new pipeline runner for the five pipeline-kind suites, which drives the real `initializeSecurityMiddleware` pipeline with a recording agent handler for event-name pinning under fail-closed xfail-baseline semantics. The pipeline gate is 35 passed, 0 failed, 0 xfail, 0 config divergences (spec 4.1.0); the detect corpus stays 184/0/0/0
- Parity: the family response and event contract is adopted across the checks, closing the last documented TS divergences. Detection blocks answer 400 `Suspicious activity detected` (replacing the legacy 403 `Access denied`) with the reference log-format on_block reasons, rate-limit blocks answer 429 `Too many requests` with `Retry-After` set to the tripped tier window and per-tier middleware events (dynamic_rule_violation endpoint, decorator_violation route/geo, global without a tier) with tier fall-through to the global counter, ip_security gains the deny reasons (`IP not in global allowlist`, `IP not in global blocklist`, `IP from blocked country`) with `ip_blocked`/`decorator_violation` events and the 403 `Forbidden` body, `user_agent_blocked` replaces `ua_blocked` with the reference route/global event split and the `User-Agent not allowed` body, the disabled-by-decorator sentinel emits the `decorator_violation` `detection_disabled` event, and `emergency_mode` renames to `emergency_mode_block`, `cloud_detection` to `cloud_blocked` per the reference EVENT_ table
- Parity: the reference behavior-rules surface is ported. New `globalBehaviorRules`/`behaviorScanResponseBody`/`behaviorMaxResponseBodyInspectBytes` config (fail-closed validation rejects body-pattern return rules with scanning off), the `BehaviorTracker` rebased on the reference sliding-window/action-dispatch semantics with bounded local stores and ban dispatch through the `IPBanManager`, and the `ProcessResponse`-equivalent pass in `ErrorResponseFactory.processResponse` driving route return rules then the global ones with `correlate_with_detection` threshold halving
- Parity: the route decorator's `ip_whitelist`/`ip_blacklist` stage semantics are aligned with the family ports (route blacklist denies first, a configured route whitelist takes over the route verdict, families never cross)
- The live dockerized smokes are pinned to the family response contract: the settled 400 `Suspicious activity detected` block body and the default `Too many requests` 429 body (custom 429 bodies keep overriding the default)

### Changed

- Adapters: the published dependency on `@guardcore/core` is now a real semver floor (`^4.2.0`) instead of the `workspace:*` protocol leaking into the published manifests (the published 4.0.4 artifacts carry the unresolvable literal); a root pnpm override keeps the workspace linked for development and CI

### Note

- The 4.1.0 family tags were a version-accuracy error and the 4.1.0 npm artifacts were unpublished. This release republishes the train correctly at 4.2.0, matching the engine (guard-core 4.2.0, spec 4.1.0 corpus)

## [4.1.0] - 2026-09-26

### Added

- Per-route detection exclusions: the reference's route-level detection exclusion surface is now ported and reachable from every adapter (the go family's guard-core-go #28 shape). New `RouteConfig` fields - `excludedDetectionHeaders`, `excludedDetectionParams`, `excludedDetectionBodyFields` (`Set<string> | null`), `enabledDetectionCategories` (`Set<string> | null`) and `detectionScanBody` (`boolean | null`), null being the inherit-the-global sentinel - are resolved per request by `resolveDetectionExclusions` (core/routing/detection-exclusions.ts), the twin of the `_resolve_*` helpers in guard_core/_utils/detection_config.py: a non-null route set replaces the global one while the header set always merges the hardcoded proxy-identity defaults with the config set and the route set, all names resolve lowercased, `enabledDetectionCategories` filters which categories can produce a threat (an empty set disables every category on that route), and `detectionScanBody: false` skips only the body surface while headers, params and the URL path still scan. The global knobs arrive too: `enabledDetectionCategories` (default: every pattern-table category, unknown entries fail config parsing like the reference validator) and `detectionScanBody` (default true) on `SecurityConfig`. The `ContentFiltering` decorator mixin gained `detectionExclusion({ headers, params, bodyFields, categories, scanBody })` writing those fields. Because the adapter middlewares never populated `request.state.guardRouteId`, decorator-registered route configs were unreachable at runtime; the adapters gained the wired surface instead: a `routeConfigs` option on express `createSecurityMiddleware`, fastify `guardPlugin`, hono `createGuardMiddleware` and the nestjs `GuardModule` (entries of `{ method?, path, config }` matched against the request path, exact or `/*`-prefix, longest path first), resolved by a registry on `RouteConfigResolver` (a direct per-request override wins, then a decorator routeId, then the path registry), plus fastify's native per-route `config: { guardRouteConfig }` route option. On the way the fastify plugin is now wrapped with `fastify-plugin`: its hooks previously landed in an encapsulated child scope, so routes registered on the app were never guarded at all; the wrapped plugin applies to the registering instance, and the integration tests cover real express/http, fastify/inject, hono/app.request and the nest middleware end to end
- Auth completeness: the required-headers and authentication surface now mirrors the reference checks field by field (guard_core/core/checks/implementations/required_headers.py and authentication.py, guard_core/decorators/authentication.py, guard_core/decorators/route_config.py). `RequiredHeadersCheck` ports the reference's message split - 400 `Missing required header: X` for absent headers and 400 `Header 'X' does not match the required value` for wrong values (replacing the single merged `Missing or invalid required header` message) - the `required` presence-only sentinel, the suspicious `logActivity` line, the `decorator_violation` event scoped by the reference's `_classify_header_violation` (x-api-key as authentication/`api_key_required`, authorization as authentication/`required_header`, anything else as advanced/`required_header`, with the `missing_header`/`mismatched_header` metadata key) and passive mode returning null after the log. `AuthenticationCheck` ports the full reference surface: the presence-only `authorizationHeaderRequired` path (mutually exclusive with authenticated routes, checked before any credential resolution), `extract_credential` bearer/basic/general extraction with the exact reference reasons, verifier resolution with route-level `authVerifier`/`apiKeyVerifier` winning over the global `authVerifier` `SecurityConfig` field, the api-key credential read from the route-named header case-insensitively, the reference failure ladder (`Missing API key`, `No auth verifier configured`, `Authentication error` on a throwing verifier, `Authentication failed` on a falsy result) all answered 401 with the reference's `Authentication required` default message (subject to `customErrorResponses`), the `decorator_violation` event carrying `authType` and `violation_type`, `state.auth_principal` set on success, and passive mode returning null after the suspicious log. The decorators gained the reference's missing knobs: `requireAuth(type, verifier)`, `apiKeyAuth(headerName, verifier)` (now stamping `apiKeyHeader` and the `required` sentinel required-headers entry instead of an empty-string expectation), and `requireAuthorizationHeader(scheme)` with the reference's mutual-exclusion ValueError ports. Previously the port had none of this: no verifiers (so an authenticated route was unpassable through the check), no presence-only path, no api-key header name, and single-message required-header failures
- Failure-policy knobs, block hook and log-redaction config: the reference's behavior knobs for failed backing services and observability hooks are now ported (guard_core/_security_config_fields.py). New `SecurityConfig` fields: `failSecure` (default true, the reference `fail_secure`: a check that raises is answered 500 `Security check failed` instead of silently swallowed, so check bugs surface; `false` restores the old log-and-fall-through fail-open), `redisFailOpen` (default false, the reference `redis_fail_open`: a `GuardRedisError` raised by a live Redis client during a check skips that failing check with a warning instead of the fail-secure 500, so `failSecure` stays the single source of truth for every other failure), `routeResolutionStrict` (default false, the reference `route_resolution_strict`: a routed request whose config lookup fails - decorator without `getRouteConfig`, unknown route id, throwing lookup - is blocked 500 `Route resolution failed` instead of running with no per-route config, while unrouted requests still pass; the `RouteConfigResolver` now records `state.guard_route_unresolved` for those cases and `RouteConfigCheck` enforces it, logging the reference's unresolved-route reason, emitting the `route_unresolved` event and honoring passive mode), `onBlock` (the reference `on_block`: best-effort hook fired exactly once per blocked request with the `(request, payload)` shape of the reference `build_block_payload` - `check_name`, `reason`, `trigger_info`, `passive_mode`, `client_ip`, redacted `path`, `method`, `status_code` - never fired for `custom_request`, `custom_validators` or the `https_enforcement` redirect, a raising or rejecting hook is caught and logged), `onError` (the reference `on_error`: best-effort `(stage, error, context)` callback wired to the `agent_init`, `geoip` and `transport_send` failure sites; the reference's `encryption` stage has no TS surface) and the redaction triple `logSensitiveHeaders` / `logSensitiveParams` / `logSensitiveBodyFields` (string arrays, empty by default, merged case-insensitively with the hardcoded default sets - `DEFAULT_SENSITIVE_LOG_HEADERS`: authorization, proxy-authorization, cookie, x-api-key; `DEFAULT_SENSITIVE_LOG_FIELDS`: access_token, refresh_token, api_key, apikey, token, password, secret, client_secret, signature). The new `redaction.ts` module ports the reference's value masking (`redactUrlForDisplay`, `redactBlobForDisplay`, `redactHeaderValueForDisplay` with the `[REDACTED]` marker: sensitive JSON keys at any depth, `name=value` / `name: value` pair scanning with bounded percent-decoding, netloc password masking) and the pipeline redacts configured sensitive names out of check-error log lines and block-payload paths; check-error messages, block payloads and the Redis handler are wired accordingly (`RedisManager` operations now raise `GuardRedisError` (503) on live-client failures, the twin of the reference `GuardRedisError`, so the `redisFailOpen` policy has a signal to key on - a null client keeps the in-memory fallback behavior). All new knobs default to the reference defaults, so behavior only changes where `failSecure`'s fail-closed default now matches the reference instead of the port's old unconditional swallow
- Cloud provider blocking: `CloudProviderCheck` now actually blocks (the port had left it a pass-through stub that resolved the provider list and returned null unconditionally). Mirroring the reference check (guard_core/core/checks/implementations/cloud_provider.py), a request whose IP falls inside a selected provider's refreshed IP ranges is blocked with 403 `Cloud provider IP not allowed`: `initializeSecurityMiddleware` wires the registry's `CloudHandler` into the check (optional constructor arg, standalone pipelines and direct constructions keep working), a `bypass(["clouds"])` route skips provider resolution entirely, whitelist and exempt_ips matches skip before any range lookup, and the per-route `blockCloudProviders` selector replaces the global list for that route (ranges still come from the refreshed global set, exactly like the reference). Blocking emits the middleware-level `cloud_detection` event plus a `decorator_violation` event scoped to route-level provider blocks, and passive mode logs the detection with `logged_only` actions while letting the request through
- Geo rate limits: the `geoRateLimits` route selector (written by the `geoRateLimit` decorator) is now enforced. `RateLimitCheck` resolves the request's country through the middleware's geoip handler and selects the matching tier from the route's map, country-specific entry first with the `"*"` pseudo-code as the fallback tier (guard-core `RateLimitCheck._check_geo_rate_limit`, tier selection matching guard-core-go `RateLimitManager.tiersFor`), then applies that `[requests, window]` pair as an endpoint-scoped tier per IP and endpoint, positioned between the route/endpoint tiers and the global tier. Without a geo handler (or with no matching entry and no `"*"` tier) no geo limit applies and the request falls through to the default global limit, exactly like the reference; passive mode logs the geo violation and keeps the request flowing. Previously the field was written by the decorator, stored on the route config and never read by the engine
- Autoban engine: the port's `banIp` had zero callers, so an attacker could violate penetration detection forever and `autoBanThreshold`/`autoBanDuration`/`enableIpBanning` were dead configuration. The reference autoban engine is now ported end to end (guard_core/core/checks/helpers.py `_increment_suspicious_counts` / `_resolve_and_apply_threshold_ban` / `_try_threshold_ban`, the SuspiciousActivityCheck threshold stage, and RateLimitCheck `_record_rate_limit_autoban`). Violations accumulate per IP and detection category in the shared counter (`GuardMiddlewareProtocol.suspiciousRequestCounts` is now `Map<string, Map<string, number>>`, the shape of the reference `suspicious_request_counts` dict-of-dicts, with the same 10,000-IP oldest-eviction cap and category totals); the detection categories ride on the scan result (`DetectionResult.threatCategories`, the twin of `DetectionResult.threat_categories`, built from regex row categories and semantic attack types exactly like `_build_detection_hit`). When a violation fires in active mode, `SuspiciousActivityCheck` first tries the `threatBanConfig` entry for each matched category in order and then the flat `autoBanThreshold`/`autoBanDuration` against the IP's category total; a crossed threshold bans the IP through the shared `IPBanManager` (wired from the registry into both checks like the #73 pattern) and the crossing request is answered 403 `IP has been banned`, with every later request stopped by the existing ip-security dynamic-ban stage. New config: `threatBanConfig` (`Record<string, { threshold, duration }>`, keys are the detection categories plus the `rate_limit` pseudo-category, unknown keys fail validation at construction) and `enableRateLimitAutoBan` (default false, so zero behavior change unless enabled): with it on, each active-mode rate-limit violation across the route, endpoint and global tiers increments the `rate_limit` category and runs the same threshold logic with `threatBanConfig['rate_limit']` overriding the flat pair. Passive mode counts violations but never bans and never blocks, `enableIpBanning: false` disables ban creation entirely, and `IPBanManager.banIp` now returns a boolean (the reference `ban_ip`) so a refused ban is distinguishable. The pre-existing 403 status for a plain suspicious-activity block is kept (the reference answers 400 there); everything else mirrors the reference
- Detection: the reference's excluded-header detection surface is now available: the hardcoded proxy identity set (the 24-entry `_DEFAULT_EXCLUDED_HEADERS` port: host, user-agent, accept, accept-encoding, connection, origin, referer, the sec-fetch and sec-ch-ua families, forwarded, the x-forwarded family, x-real-ip, the client-ip family, cf-connecting-ip, true-client-ip, fly-client-ip, x-envoy-external-address) plus a new `excludedDetectionHeaders` field on `SecurityConfig` (array of header names, empty by default), merged lowercased into the routing set. An excluded header is no longer skipped from the scan: like the reference's `_scan_excluded_header_component` it scans with every enabled category except the ssrf skip resolved per value (`_excluded_header_skip_categories`), so a bare `x-forwarded-for: 192.168.65.1` no longer false-positives ssrf while an attack payload in the same header still detects. The skip is resolved by the new `HeaderExclusions` helpers in utils: address-carrying headers (host, origin, the forwarding family, the client-ip family, via) skip ssrf for any value, any other excluded header skips ssrf only when its whole value parses as an address chain (`_strip_forwarded_entry_port` plus comma-token `node:net` isIP parsing, so `10.0.0.5, 172.16.0.1` reads as a proxy chain while `203.0.113.10' OR '1'='1` still detects as sqli and the always-scan cmd_injection shapes such as `${jndi:...}` keep detecting everywhere). `SusPatternsManager.detect` takes an optional `skipCategories` option so skipped-category threats never count toward the anomaly/threat decision, and the family-local sec-prefixed full skip now applies only to headers outside the exclusion set. `scanRequestWithManager` threads the resolved config's `excludedDetectionHeaders` like the two sibling exclusion fields
- Config: `exemptIps` on `SecurityConfig` (array of IP/CIDR strings, empty by default), the port of the reference's `exempt_ips` (guard-core #117/#118). It is noise reduction for known-friendly automation, not immunity: a non-empty `whitelist` denies every unlisted IP, so there was no way to let a few trusted clients (monitoring probes, VPN egress, a partner's server) skip throttling on a public API. An exempt match sets `request.state.isExempt` under the same conditions as `isWhitelisted`, computed in `IpSecurityCheck` from the deny-check outcome (`is_allowed`), so exemption never adds or relaxes a deny path; the exempt match reuses the whitelist matcher (`isIpInWhitelist`), so exact, CIDR and IPv4/IPv6-family semantics stay identical. The skip set matches the reference: `RateLimitCheck`, `UserAgentCheck` and `CloudProviderCheck` now honor `isWhitelisted || isExempt`, while `SuspiciousActivityCheck` honors `isWhitelisted` only, so penetration detection, its violation counting and its escalation still run for exempt IPs (an attack payload from an exempt IP is still blocked; a scanner needs per-route `bypass(["penetration"])`, widening the field later is backward compatible). Still applies to exempt IPs, deliberately: the blacklist, the whitelist deny path, dynamic bans and per-route `requireIp`/`blockIp` rules (a route-level `ipWhitelist` takes over the global lists and clears both flags, exactly like the reference `skip_ip_lists` gate). Entries are validated at construction like `whitelist`/`blacklist` (invalid entry fails closed). The IP check now also enforces dynamic bans (the reference `_check_banned_ip` stage the port had skipped): `initializeSecurityMiddleware` wires the registry's `IPBanManager` into `IpSecurityCheck` (optional constructor arg, standalone pipelines and direct constructions keep working), banned IPs get 403 `IP address banned` before the flag resolution, honoring route `bypass(["ip_ban"])` and passive mode. `GuardRequestState` documents the two flags
- Detection: the reference's excluded-field config surface is now available: `excludedDetectionParams` and `excludedDetectionBodyFields` on `SecurityConfig` (empty by default). `excludedDetectionParams` skips a query parameter's whole pair from penetration detection (`key.lower() in excluded_params` in `_scan_query_params`), and `excludedDetectionBodyFields` skips urlencoded form pairs and multipart parts by field name and whole JSON subtrees by key at any nesting depth: `scanRequestWithManager` now takes the resolved config (the middleware path passes it through `detectPenetrationPatterns`, the standalone path uses the default manager's config), threads the body-field exclusion into the embedded-JSON walks of query and header values, and skips excluded multipart parts via a new `exclusionKey` on each `MultipartEntry` (the disposition name, null for unnamed parts, so the `file` fallback label never suppresses a part without a name, exactly like the reference). Entries are matched verbatim while scanned names and keys are lowercased first, mirroring Python's `_STR_SET_ADAPTER` + `key.lower()` membership semantics. One routing divergence against the reference is corrected on the way: a JSON-content-type body whose walk parses cleanly is now final (the raw blob only scans on parse failure, mirroring `_scan_request_body`'s `json_hit is not None` check, the same fall-through shape as the Go and PHP ports), so an excluded JSON key's subtree stays excluded instead of leaking through the blob rescan. Verified against the reference engine: a JSON body with an excluded nested key does not detect, while the raw query value still scans after an embedded walk whose every leaf was excluded (defense in depth)
- Detection: multipart/form-data bodies are now parsed and scanned part by part instead of falling through to the whole-body blob scan, completing the family's body-surface parity (guard-core commit 5f399234, mirrored by the merged Go and PHP ports). A hand-rolled line-based scanner mirrors the reference email-parser tolerances: preamble and epilogue discarded, raw header names and case kept in wire order, folded header continuations preserved with their raw break, the first colonless line opening the payload, the line terminator before a boundary belonging to the delimiter, nested multipart containers walked in place, and a missing closing boundary keeping the part parsed so far. Each leaf part scans its field name, then its filename entry (`filename="..."` with RFC 7578 quote unescaping and get_filename's RFC 2231 `filename*` fallback), every part header, and the payload under `request_body:multipart_field`; a body that does not parse into at least one leaf part (no boundary parameter, boundary mismatch) keeps the whole-body blob fallback
- Detection: binary-dense file-part payloads are reduced to printable islands before pattern scanning. A part payload whose binary artifact characters (control bytes, U+FFFD, surrogate-escaped bytes) fill at least a fifth of it is cut into its maximal printable runs, and only runs of at least `detectionBinaryMinRunLength` (new SecurityConfig field, default 16, bounds [4, 1024]) are handed to the scan as individual values, so compressed or encrypted uploads stop producing attack-shaped matches whose rate grows with file size while text embedded in uploads (a script inside a PDF, a path inside an archive) still scans in full. Nothing detects across island boundaries; text parts without a filename and whole-body fallback scans keep their full scan so raw-body signature coverage stays intact
- Detection: urlencoded form bodies now split through a `parse_qsl(keep_blank_values=True)` port (valueless names kept, empty chunks dropped, plus-as-space, tolerant percent-decoding with valid UTF-8 runs decoded as text), replacing the `URLSearchParams` iteration whose semantics drifted from the reference on edge cases

### Fixed

- Docs: the `geoRateLimit` decorator documentation showed a `DEFAULT` fallback key that never existed in the engine; the enforced fallback tier key is `"*"`, matching the reference (guard-core and guard-core-go). The docs now also state the geoip-handler requirement for the tier to apply
- Detection: separator-prefixed recon probes such as `\default` or `\README.md` scanned in query, body or form-field values now detect again. The configured pipeline's preprocessing folds LDAP hex escapes (`\de` into `Þ`) before the pattern table runs, so the probe arrived mangled on the processed views, and the recon-category rows were excluded from the raw view, leaving no view that saw the original value. All 21 recon rows now join the signal-preserving raw view (a `DETECTION_RECON_RAW_VIEW_PATTERN_SOURCES` set derived from the table, mirroring `guard_core/handlers/_suspatterns_pattern_table.py`, upstream commit 81cf07f1), their processed-view runs stay intact, the #116 leading-separator probe gate applies unchanged to raw-view matches (bare words stay innocent outside url_path/unknown), and raw-pass threats are deduplicated against the processed-view threats keyed on (pattern, match text) so a row matching both views counts once. Parity with guard-core-rs #21, guard-core-go #16 and guard-core-php #16
- Detection: the live middleware now runs the FULL canonical pattern table through `SusPatternsManager.detect` for every request surface (query param names and values, URL path, header names and values, JSON body keys and leaves, form fields, raw blob), exactly mirroring the reference detect flow (`guard_core/_utils/penetration_detection.py` + `detection_scan.py`). Previously the `SuspiciousActivityCheck` only ran a hardcoded 7-pattern shortcut, so the TypeScript middleware detected far less than every other family: recon probes, tautologies, event-handler XSS, NoSQL operator keys and all case/encoding variants that live only in the 157-row table were missed. JSON leaves embedded inside non-body values carry the `:embedded_json` context suffix so the engine's per-context gates (recon bare-word rule, source-extension probe rule) apply to them; body JSON values scan as `request_body` per the reference context matrix. The retired 7-pattern shortcut path is gone; the public `detectPenetrationAttempt` export now delegates to the same engine on a shared default manager
- Adapters: block and error responses are `text/plain; charset=utf-8` carrying the message itself, instead of `application/json` wrapping it in a `{detail: ...}` envelope, mirroring the Python family convention (fastapi-guard #144). Applies across the express, fastify, hono and nestjs response factories (redirect responses keep no body, custom_error_responses messages stay plain text), and a `customResponseModifier` that sets its own content type still wins
- Detection: recon whole-value rows with an optional leading path separator no longer flag bare words such as "default" or "README.md" scanned in query/body contexts; bare words remain probes as the url_path (or in unknown contexts) and separator-prefixed paths are still threats. Parity with guard-core #115/#116 (commit 08f79d67)
- Logging: `sanitizeForLog` now emits pure ASCII like the reference `_sanitize_for_log` (guard-core commit f5d53ca5, log half). Control characters and every non-ASCII code point become `\uXXXX` escapes (lone surrogate-escaped bytes in the 0xDC80-0xDCFF range become `\xNN`), so log lines can never raise on legacy code pages such as Windows cp1252

## [1.0.0] - 2026-03-27

### Initiial release

- Initial release of the @guardcore TypeScript ecosystem
- **@guardcore/core**: Framework-agnostic security engine (TypeScript port of guard-core Python)
  - 6 protocol interfaces (GuardRequest, GuardResponse, GuardResponseFactory, GuardMiddlewareProtocol, GeoIPHandler, AgentHandlerProtocol, RedisHandlerProtocol)
  - 44-field SecurityConfig with Zod validation and cross-field validators
  - 17-check SecurityCheckPipeline (Chain of Responsibility pattern)
  - 75 suspicious pattern definitions with 17 context sets
  - Detection engine: PatternCompiler (re2-wasm + worker_threads fallback), ContentPreprocessor, SemanticAnalyzer, PerformanceMonitor
  - 9 handlers: RedisManager, IPBanManager, RateLimitManager, CloudHandler, SusPatternsManager, SecurityHeadersManager, BehaviorTracker, DynamicRuleManager, IPInfoManager
  - HandlerRegistry pattern (no global singletons, test-friendly)
  - 20-method SecurityDecorator with TypeScript mixin composition
  - Full utils module: IP extraction, penetration detection, logging, agent events
  - Edge runtime support via Uint8Array protocols and re2-wasm
- **@guardcore/express**: Express middleware adapter with raw body preservation
- **@guardcore/fastify**: Fastify plugin adapter with onRequest/onSend hooks
- **@guardcore/nestjs**: NestJS middleware + GuardModule.forRoot() with DI
- **@guardcore/hono**: Hono middleware factory (edge-safe, lazy initialization)
- 681 tests with 100% statement/line coverage across 31 test files
- Comprehensive CLAUDE.md with TypeScript development standards
